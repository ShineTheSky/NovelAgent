# History 作为普通记忆来源的实施计划

## 边界

- 文件修改：以一次用户请求内、同一文件的修改过程为 History 单元。需求与 Ask 回答先进入请求记录；写作、审阅、润色和主 Agent 直接写入产生的版本归到对应文件单元。整轮结束后才分析，每个文件一次。
- 纯对话：没有文件单元的请求形成对话 History。LLM 从已有 Session turn 中选择相关范围；程序校验范围并保存原始回合及实际模型上下文。一次请求可能跨多个 Trace 段，所以保留多个 Trace ID。
- 明确无需修改：记录评价事件并锚定被评价的版本，不创建正文版本。
- 失败／中断：保留已收集证据和已提交的版本；下次同文件修改关联前次失败尝试。失败单元不自动提炼为普通记忆。
- Trace：继续保存完整执行证据、bad/bash case 和压缩窗口摘要；定期窗口及 Ask 不直接提炼普通记忆。`CreateTraceCheckpoint` 只影响诊断摘要边界。

## 实施顺序与验收

1. 扩展项目 `.history/history.sqlite3`，添加请求／文档／对话单元、有序事件、状态、Session turn 范围和分析准备结果。验证多次 Ask、多个文件和连续版本不会互相覆盖。
2. 接入主循环、子 Agent、写入工具及无需修改工具。验证写作→审阅→润色只在请求结束后对同一文件分析一次；纯对话形成独立单元。
3. 增加 History 提炼器，复用现有语义场景提示词和 Insight／Memory／Pattern 文件生命周期。来源键使用 History ID，旧 Trace 来源保持可读；分析重试不重复加权。
4. 将生产 Trace 窗口改为只生成压缩摘要，恢复任务亦如此；bad/bash case 不变。验证上下文压缩仍能读取窗口摘要。
5. 加入失败与重启恢复测试；运行相关测试和全套测试。对旧数据只做兼容读取，不从旧 Trace 推断不存在的 History。

## 尚需后续确认的迁移问题

既有 Trace 派生的 Memory 不强行迁移来源；新 History 记录可在合并时引用它们。旧的手动 Trace 分析接口改为调度待分析 History，避免混合来源重复提炼。

## 本轮实施状态

上述生产路径已接入；旧 `FileTraceAnalyzer.analyze()` 保留供历史回放与既有测试使用，但定期窗口及手动待分析接口不再调用它提炼普通记忆。History 提炼所用 LLM 的真实服务端效果仍需在有模型连接的项目会话中验收；单元测试使用可控响应验证了来源校验、关闭时机、重试去重与摘要隔离。
