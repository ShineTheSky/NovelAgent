# 文档 History 需求与代码影响评估

状态：文档 History 主路径已实施。本文定义以创作文件为中心的 History；不把 History 当作 Memory，也不要求文档 History 依赖原始 Trace。无文件目标的项目讨论继续由现有 Trace 分析处理，独立的 Project History 留待后续设计。

## 目标与边界

- 以文件为单位还原每次生效的正文：它从哪个版本修改而来、当时依据哪个版本的卷纲和章纲、哪些原始需求和 Agent 思考促成了它。
- 当前创作文件继续使用 `workspace/{project_id}/` 下的 Markdown。建议在项目内使用 SQLite 保存可按文件、版本和需求检索的 History，包括每一版的完整 Markdown 正文。工作区文件是当前版本的可编辑呈现；两者必须用修订 ID 和正文哈希校验。
- History 保存原始事实和明确作出的“无需修改”决定，不预先判定需求是否落实、Agent 哪里出错、用户有什么长期偏好。这些结论由后续 Memory 分析产生。正文 diff 由当前版和父版按需计算，不重复作为原始证据存储。
- 文件 History 已保存其所需的完整原始证据时，不以 Trace ID 作为必需外键。Trace、bad case、bash case、会话压缩的现有用途不因本需求而删除。无文件目标的项目讨论也不硬挂到文件版本上；其 Project History 来源另行设计。

## Memory 中的语义证据

文件记忆的来源链为 `History → 语义提取 → 含 semantic_evidence 的 Memory/Insight`。`semantic_evidence` 不再是从 Trace 窗口另存的 Bank 节点，而是针对 History 中一个或多个文件版本及其需求、审阅和创作过程，提取出的**更精确、可独立理解的记忆证据与语义信息**。它随记忆候选保留，组成后续合并、反思和精炼所需的基础内容；本身不等于原始 History，也不能单独宣称为已确认的 Memory。

- 每条语义证据要保留其主张或观察、适用对象与条件、谁提出或执行、必要的原文摘录、确定性与尚缺的信息，以及可定位的 History 版本/证据 ID。明确区分用户要求、审阅发现、Agent 判断和提取器推断；不得把后两者改写为用户已确认的偏好。
- 对同一 History 可以重新提取或修正语义证据，但不能改写原始 History。Memory 必须能回溯到支撑它的语义证据及 History；多条语义证据合并时保留各自来源，不因文本相似就视作独立支持。
- 日常合并、反思和精炼先读取相关记忆及其 `semantic_evidence`。只有其中的摘录、适用范围、冲突关系或因果链不足以支撑判断时，才按所存 History ID 回读相应版本、完整需求线及原文；仍不足时标记证据不足，不凭空补足。不要默认读取整个文件历史或原始 Trace。
- 语义证据可从 History 重新提取，须与原始 History 分清权威性。物理上可以是记忆记录的字段或关联表，但不再作为独立的 Bank 来源层维护。

## 版本与证据归属

一次**生效的正文修改**产生该文件的一个新版本；审阅本身不修改正文，因此不产生版本。文件的版本链独立于其他文件。若同一 Agent 任务实际多次持久化正文，每次生效写入都必须可追溯；不能覆盖中间稿后声称保存了每次修改。

| 场景 | History 归属 |
|---|---|
| 首次写作 | 创建文件 v1，记录写作需求、传递任务和写作 Agent 的可记录思考。 |
| 审阅 v1 后润色 | 审阅证据和润色过程归入形成的 v2；v2 的父版本是 v1。Reviewer 只输出报告，不单独增加正文版本。 |
| 用户评价 v2 后再次润色 | 用户原话、主 Agent 实际传递的任务和润色过程归入形成的 v3；v3 的父版本是 v2。 |
| 明确决定无需修改 | 不产生空的正文版本；意见、明确的“无需修改”决定及当时给出的依据保留在被评价的当前版本。执行失败或中断不得冒充“无需修改”。 |
| 一轮需求修改卷纲、章纲和小节 | 只有实际改动的文件各自增加版本；使用同一操作 ID 关联这轮修改。下游新版本记录实际依据的上游版本，不能事后按“最新版”推断。 |

每个促成新版本的需求有两条可能并存、但不得混成一段摘要的原始证据线：

1. **用户线**：用户输入原文，包括被引用的原文和 AskUserQuestion 选项的完整内容；主 Agent 实际传递给执行 Agent 的任务原文。
2. **审阅线**：审阅 Agent 实际可记录的思考、审阅输出，以及实际传递给写作/润色 Agent 的内容。若报告与最终传递内容不同，两份都保留。

同一新版本可以同时关联多条用户线和审阅线。写作、润色 Agent 的实际可记录思考与对应版本关联；不得凭输出倒推或编造未记录的内部思考。证据可在正文修订形成后补齐，但补证据不增加正文版本号。

## 逻辑数据内容

以下是必须表达的逻辑记录，不限定最终 SQL 表名：

| 记录 | 必要内容 |
|---|---|
| 文件 | 稳定文件 ID、当前路径、最新修订指针。历史路径随修订保留，避免改名后失联。 |
| 正文修订 | 修订 ID、该文件内的版本序号、父修订 ID、完整 Markdown 正文、正文哈希、产生该修订的操作 ID 与时间。首次写入没有父修订。 |
| 上游依赖 | 本修订实际依据的卷纲、章纲的文件 ID 与**当时的修订 ID**；其他确实被用作约束的文件可同样记录。文件名规则负责定位，不能代替历史版本号。 |
| 需求证据 | 来源类型、完整原文、实际传递文本、关联的文件修订；引用具体段落时保存用户提供的原文，不能只存摘要。 |
| 执行证据 | 写作/润色 Agent 的角色、与该文件修订相关且实际可获取的思考原文。技术性运行 ID 可用于把同一轮多文件修改归组，但不以原始 Trace 作为必需内容。 |
| 无修改记录 | 被评价的当前修订、意见原文、明确的“无需修改”决定及其原始依据；不创建新正文修订。 |

History 中不写“已落实/部分落实”“问题根因”“记忆类别”等事后分析结论。依赖关系、原文证据和处理决定仍须保留原始时间顺序，供之后的 Memory 提取与纠错使用。

## 存储与读取约束

- 每个项目使用独立的 `.history/history.sqlite3`。SQLite 是 History 的权威版本库，当前 `.md` 是工作副本；数据库保存完整正文而不是只保存 diff。
- 最新版通过文件的最新修订指针读取；旧版通过修订 ID 或“文件 ID＋版本序号”读取。版本号和关联字段建立索引。构造模型上下文时只提取命中的版本与证据，不把某文件全部历史直接注入。
- 一次数据库提交应原子地写入正文修订、已知依赖和证据关联并更新最新修订指针；不得在等待 LLM、审阅或用户回复期间保持写事务。多个文件在一轮任务中可按实际完成顺序提交，并以操作 ID 归组。
- 数据库事务不能同时覆盖外部 `.md`。文件写入、数据库写入和启动恢复需有一致性协议：不把“文件已改而 History 未记录”静默报告为成功；若检测到外部修改或哈希冲突，应保留内容并明确暴露差异，不能覆盖。
- 现有项目首次纳入 History 时，只能把可核验的当前文件导入为基线。现有 frontmatter、短摘录或 Trace 不足以还原的旧正文，不得伪造为完整历史版本。

| 范围 | 当前情况 | 需要修改的方向 |
|---|---|---|
| `novelagent/versioning.py` | 生成修订 ID、父 ID、正文哈希并原子替换当前 Markdown，但不保存完整旧版。 | 与 History 的提交/恢复协议对接，保留现有预期修订冲突检查；明确正文版本与后补证据的边界。 |

| 新的 `novelagent/history/` 存储层 | 尚不存在。现有 SQLite 在 `novelagent/storage/database.py` 中集中管理全局 `data/novelagent.db`。 | 增加项目级 History schema、索引、按版本读取、证据关联、无修改记录及一致性恢复；不让现有 Trace 表直接承担文件 History。 |

| `docs/project-storage-layout.md`、`docs/memory-layout.md` | 尚未定义 `.history/`，记忆说明仍写 `Trace → Memory → Rule`。 | 实施时同步说明 History 与 Trace、Memory 的不同职责；本需求文档不冒充已实现结构。 |

## 验收条件与测试

1. 首次写作得到 v1；审阅本身不新增版本；润色写入得到 v2；随后用户反馈与再次润色得到 v3。每版能取回完整正文、父版本、两条需求线及相关 Agent 思考。
2. 基于 v1/v2 正文可按需计算 diff；只补充证据或明确“无需修改”时正文版本号不增加。未产生修改时，意见留在当前版本且有明确依据。
3. 修改卷纲、章纲、小节后，各文件独立递增；小节新修订的依赖指向实际使用的上游修订，同轮修改可按操作 ID 关联。
4. 按文件取最新版本、按修订 ID 取旧版、按文件列版本链均不需要扫描所有项目 History；引用原文、AskUserQuestion 选项完整内容和实际传递任务不丢失。
5. 修订冲突、History 写入失败、文件/数据库不一致和启动恢复均有测试；不能留下“工具报告成功但修订历史缺失”的状态。既有文件只导入可验证基线。
6. 文档 History 查询与记忆提取不要求原始 Trace 存在；现有 bad case、bash case、上下文压缩及项目对话的 Trace 功能仍可运行。
7. 能从 v1→v2 的完整 History 提取带来源、范围和不确定性的语义证据并随记忆候选保存；合并与反思通常读取记忆及这些信息，在不足或互相冲突时才按 History ID 回读原始版本与需求线。不能把派生语义证据当作未加工的用户原话。

优先新增 History 存储与修订链测试，再做写入边界、证据收集、语义证据提取和记忆来源迁移的集成测试。现有 `tests/test_memory_bank.py`、`tests/test_trace_feedback.py`、`tests/test_trace_semantic_extraction.py`、`tests/test_agent_loop_helpers.py`、`tests/test_agent_run_trace.py` 和审阅工作流相关测试需随职责迁移复查；不能仅以原 Bank 测试通过作为新 History 的验收。
