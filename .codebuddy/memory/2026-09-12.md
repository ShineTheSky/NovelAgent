## Trace 分析分支机制核查
- 聚合 Trace 时会复制当前 `ctx.to_llm_messages()` 到 SQLite `trace_snapshots.messages_json`；随后异步调用 `PostTurnAnalyzer.analyze(trace_id, project_id, captured_messages, tool_schemas)`。
- Analyzer 以该快照为 messages 前缀，再追加一条明确禁止继续主对话/调用工具、仅做记忆提取的 user prompt；这是 LLM 上下文的只读分支，并不复制 Session 或让主链路等待。
- Trace 事件是该分支的可作为长期记忆证据的限定数据源；分析结果写 SQLite trace_memories/memory_patterns，不写项目 `.memory/`。
- 该快照含当前**已渲染的 system prompt**（工具描述、.memory 索引、confirmed preference context 等）及该请求已构建的完整消息序列（历史、当前输入、RAG 与预取记忆系统消息、回合内工具消息）；但不含运行时 ToolContext、权限状态、请求元数据等非消息对象。工具 schema 会作为独立参数给分析 LLM，但分支任务明确禁止工具调用。
- Trace 捕获接口返回 trace_id、回合范围和消息快照；后续 Analyzer 自己不返回业务结果，而将模型输出的有效候选直接创建为 SQLite `trace_memories`（携带 source_event_ids 作为证据链）。preference/issue 还会创建或关联 `memory_patterns` 并审核；`project_fact` 仅创建原子记忆。不创建旧 `.memory/*.md` 文件。数据库固定为仓库根目录的 `data/novelagent.db`。

## Trace 与记忆的双层设计共识
- 用户确认：数据库不是 Memory 真相源，而是完整、不可变的 Trace 原始库；`.memory/` 是 LLM 可读写的记忆快照层，保存已提炼记忆、候选/待升级证据和 Pattern。
- 大部分无长期价值的 Trace 只留在数据库；证据文件在 frontmatter 中保存 session_id、trace_id、event_ids。后续新证据关联既有候选时，Agent 可回读该 Trace 及其前后窗口补足语境，再进行 Pattern 升级、合并或冲突判断。
- 用户倾向不为每条 Trace 单独保存完整 context snapshot：若数据库的不可变 trace_events 能完整保存用户/回复/工具/错误等可分析事实，则证据引用已足够；仅当需精确复原完整 LLM 输入或 events 不完整时，snapshot 才保留。当前 TraceRecorder 尚未实际记录细粒度事件，不能直接删除现有 snapshot。

## Session/Trace 合流核查与目标
- 当前 `sessions.messages_json` 是用于下轮 LLM 恢复的完整可变消息快照，每个工具 ReAct 轮次结束与 SSE finally 整包覆盖保存；自动压缩会用摘要+最后四条非 system 消息替换历史。`session_trace_turns` 追加保存用户输入+最终回复，达到间隔再复制为 trace_events，因此与 session 和 Trace 都重复且内容不一致。
- 曾讨论合流方案：一条 append-only `session_events` 原始事实流，事件带 trace/run ID；session 消息快照为可覆盖投影。该方案**已被用户否决**，不实施。
- 用户最终决定 Session 与 Trace 分开：Session 仅用于下一轮 LLM 上下文（允许压缩、覆盖）；Trace 独立写入数据库，承担原始执行事实、审计、回放和证据回读。`.memory/` 继续保存提炼的记忆快照、候选证据和 Pattern。
- 补充决策：Memory 直接保存对应 trace_id（必要时 session_id/event_ids）；Evidence 升级为 Memory 后即被其取代，不保留独立 evidence_id。Pattern 即长期 Rule，记录支持/冲突的 memory_id，利用各 Memory 的 Trace 引用回读原始事件窗口，再由 Agent 做合并或冲突语义判定，不能只依据 Markdown 摘要，以避免误伤。
- 现有代码没有 Memory 领域的 `Rule` 实体；仅有旧 SQLite `memory_patterns` / `pattern_memories` 结构（现已停用、保留 schema/API 兼容），`rule` 一词仅用于安全权限规则。用户决定后续仍命名为 `Pattern`，不引入 Rule 术语；Pattern 除支持/冲突的 memory_id 外，还显式记录其关联 trace_id，作为直接回读数据库原始上下文的索引。关联由 LLM 每次总结/分析时填写候选值，但程序必须验证 Memory、Trace 的存在性、项目归属以及 Memory↔Trace 溯源一致性，拒绝模型幻觉引用。
- 当前 Trace ID 为全局 UUID（`tr_` + uuid4 hex），字符串不内嵌 session_id；`traces` 表以 trace_id 主键并另存 session_id，因此跨 session 不会同名。用户决定 Memory 仅保存 trace_id（及可选 source_event_ids），session_id/project_id 从 Trace 反查，避免冗余 ID；程序校验 trace_id 的项目归属。
- 说明：数据库目前保存 Trace 头（trace_id/session_id/project_id/状态）、聚合事件、会话 Trace 回合、分类和完整消息快照；因此 trace_id 可追溯会话/项目/已捕获上下文。但主循环尚未启用 TraceRecorder 的细粒度事件记录，工具/权限/错误等并非都作为独立事件入库，需后续补齐才能满足“完整原始事实库”目标。

## 后续改造总方案（用户确认的设计）
- Session 保持独立，仅为下一轮 LLM 的可变、可压缩上下文快照；不与 Trace 合流、不作为原始历史。每次请求创建一条独立 Trace，Trace 通过 trace_id 绑定 session/project。
- 接通 TraceRecorder：请求开始创建 Trace，记录用户/LLM/工具调用与结果/权限/问答/错误/完成等已脱敏事件；finally 写 Trace 终态。事件完整后去掉 session_trace_turns 聚合和按间隔捕获逻辑，并停止保存完整 context snapshot（仅保留可选 prompt 版本或哈希）。
- `.memory/` 分为 Evidence、Memory、Pattern：Evidence 是 LLM 判断尚无法形成长期结论、需等待后续支持的临时文件，保存 trace_id + source_event_ids；支持充分后提升为 Memory 并删除 evidence_id。Memory 保存 trace_id + source_event_ids，Trace 仍为 SQLite 原始库。新增文件化 `.memory/patterns/`，Pattern 保存支持/冲突 memory_id 与 LLM 提议的 trace_id。
- Pattern 合并/冲突：LLM 提出候选 ID；程序验证文件/数据库存在、同项目归属与 Memory↔Trace 一致性；再根据 trace_id/event_ids 回读原始事件窗口，由 LLM 作最终语义裁决。confirmed Pattern 由文件扫描后高优先级注入上下文。
- API/UI 改为读取文件化 Pattern；SQLite trace_memories/pattern 表停止写入且后续清理。补全端到端测试：成功、工具错误、权限问答、中断、压缩及跨 Trace 合并/冲突。
